# booking-bot

Telegram-бот и backend для онлайн-записи в салон, к частному мастеру,
репетитору или другому специалисту. Проект строится на Go с PostgreSQL и
Redis по схеме `Telegram handler → service → repository → PostgreSQL`.

## Текущий статус

Реализован backend этапа 5 — **Schedule**:

- регистрация и обновление Telegram-пользователя через `/start`;
- главное клиентское меню;
- бизнесы и членство с ролями `OWNER`, `ADMIN`, `EMPLOYEE`;
- проверка доступа к `/admin` для владельца и администратора;
- service layer и Telegram CRUD для услуг и сотрудников;
- централизованная проверка `OWNER`/`ADMIN` во всех изменяющих операциях;
- Redis FSM для многошаговых административных диалогов;
- недельное расписание сотрудника, один интервал на день;
- выходные дни;
- блокировки времени;
- Telegram UI настройки расписания и блокировок;
- настройки бизнеса: интервал начала записи, минимальное время до записи и
  максимальный горизонт бронирования;
- динамический расчёт доступного времени с учётом длительности услуги,
  расписания, блокировок, timezone и настроек бизнеса;
- автоматические миграции и graceful shutdown.

Этап 4 завершён для административного MVP: владелец и администратор могут
создавать, редактировать, активировать и деактивировать услуги и сотрудников.
Этап 5 подключён к Telegram: можно настроить рабочий день/выходной и создать
блокировку. Состояния многошагового ввода хранятся в Redis 30 минут и могут
быть отменены кнопкой «❌ Отмена».

Bookings пока не реализованы. Поэтому на этапе 5 занятость формируется из
`blocked_slots`; активные записи будут добавлены в тот же запрос на этапе 6.

## Архитектура

```text
cmd/bot/                     composition root
internal/bot/                Telegram routes, handlers, keyboards
internal/bot/fsm/            Redis-состояния многошаговых диалогов
internal/service/            бизнес-правила и расчёт слотов
internal/repository/         SQL и отображение строк БД в модели
internal/model/              доменные структуры
internal/database/           подключения и встроенные миграции
internal/config/             environment configuration
internal/apperr/             доменные ошибки
```

Handler не содержит бизнес-правила, repository не зависит от Telegram.
Зависимости service layer описаны узкими интерфейсами, что позволяет
тестировать расчёты без PostgreSQL. Авторизация выполняется повторно внутри
service layer для каждой административной операции, поэтому ручная отправка
Telegram-команды не обходит RBAC.

## Схема данных

Текущие таблицы:

- `users` — Telegram-пользователи;
- `businesses` — бизнес и его timezone/настройки записи;
- `business_members` — роли пользователей внутри бизнеса;
- `services` — услуги, длительность, цена и активность;
- `employees` — сотрудники и необязательная связь с пользователем;
- `working_hours` — локальный рабочий интервал по дню недели;
- `blocked_slots` — абсолютные периоды недоступности сотрудника.

Миграции находятся только в `internal/database/migrations` и встраиваются в
бинарник через `embed.FS`. При старте приложение автоматически выполняет все
pending migrations.

### Работа со временем

- `working_hours.start_time/end_time` имеют тип `TIME`: это локальное время
  бизнеса без привязки к UTC;
- `blocked_slots.start_at/end_at` имеют тип `TIMESTAMPTZ`: это абсолютные
  моменты времени;
- календарный день и weekday вычисляются в `business.timezone`, а результат
  расчёта слотов возвращается в UTC;
- timezone сервера не используется как бизнес-время.

## Алгоритм доступных слотов

`ScheduleService.GetAvailableSlots`:

1. Проверяет существование и активность сотрудника и услуги, а также их
   принадлежность одному бизнесу.
2. Загружает timezone и настройки бизнеса.
3. Проверяет, что дата находится между сегодняшним днём и
   `max_booking_days` в локальном времени бизнеса.
4. Находит рабочий интервал по ISO weekday (`Monday=1`, `Sunday=7`).
5. Генерирует начала с шагом `slot_interval_min`; длительность услуги не
   должна выводить окончание за границу рабочего дня.
6. Отбрасывает время раньше `now + min_booking_notice_min`.
7. Исключает пересечения с блокировками методом прохода по отсортированным
   интервалам.
8. Возвращает допустимые начала в UTC.

Используются полуоткрытые интервалы `[start,end)`: слот, начинающийся ровно
в момент окончания блокировки, допустим. Чистая функция
`ComputeAvailableSlots` покрыта table-driven тестами, включая длительность,
«дырки», границы рабочего дня, minimum notice и DST.

## Запуск

```bash
cp .env.example .env
# Укажите BOT_TOKEN от @BotFather
docker compose up --build
```

Ожидаемые сообщения в логах:

```text
migrations applied
connected to postgres
connected to redis
telegram bot started (long polling)
```

Локальный запуск:

```bash
docker compose up -d postgres redis
set -a; source .env; set +a
make run
```

Остановка:

```bash
docker compose down
```

## Environment variables

| Переменная | Обязательная | По умолчанию | Назначение |
|---|---:|---:|---|
| `BOT_TOKEN` | да | — | Telegram Bot API token |
| `DATABASE_URL` | да | — | PostgreSQL DSN |
| `REDIS_URL` | да | — | Redis URL |
| `APP_ENV` | нет | `development` | Окружение и формат логов |
| `LOG_LEVEL` | нет | `info` | Уровень логирования |
| `DEFAULT_SLOT_INTERVAL` | нет | `30` | Шаг начала записи, минуты |
| `DEFAULT_MIN_BOOKING_NOTICE` | нет | `60` | Минимальное время до записи |
| `DEFAULT_MAX_BOOKING_DAYS` | нет | `30` | Горизонт записи, дни |

Значения `DEFAULT_*` копируются в настройки нового бизнеса при его создании.

## Миграции

Автоматически применяются при запуске. Ручное управление требует goose CLI:

```bash
make migrate-up
make migrate-down
```

Обе команды используют `internal/database/migrations` и переменную
`DATABASE_URL`.

## Пользовательские сценарии

- `/start` регистрирует пользователя или обновляет его Telegram-профиль и
  показывает главное меню.
- `/admin` находит первый бизнес пользователя, проверяет роль и показывает
  административное меню только `OWNER`/`ADMIN`.
- «💈 Услуги» позволяет просматривать, создавать, редактировать и менять
  активность услуг.
- «👨‍💼 Сотрудники» позволяет просматривать, создавать, редактировать и менять
  активность сотрудников.
- «🕐 Расписание» настраивает рабочий интервал либо выходной по дню недели.
- «🚫 Заблокировать время» создаёт недоступный период в timezone бизнеса.
- Нереализованные клиентские кнопки и отчёты пока отвечают заглушкой.

## Следующий этап

Этап 6 добавит клиентский выбор услуги, сотрудника, даты и времени,
создание/отмену booking и защиту от конкурентного бронирования через
PostgreSQL exclusion constraint. При его реализации блокировка времени также
будет проверяться на пересечение с существующими активными записями.
